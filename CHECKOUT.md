Changed snapshots cannot reuse a reservation. Existing signed-webhook payment confirmation, expiry and cancellation rules apply.

# Sandbox checkout

Automatic payment-confirmation, pickup-ready and shipped emails are implemented with a private queue. They require the migration/configuration/worker in [ORDER_EMAILS.md](ORDER_EMAILS.md); they are not enabled by Supabase SMTP setup alone. Pickup scheduling remains manual. This supersedes older notification-not-implemented notes below.

This is a ready-made product checkout foundation for testing. Live Stripe keys are refused. Custom apparel is supported for sandbox testing as described above; production artwork calibration remains outstanding. This is not a production launch approval.

## Confirmed fulfilment

- Currency: CAD. Canada-wide delivery is $8.99 per order before applicable tax.
- Free pickup: 222 Bankside Drive, Kitchener, ON N2N 3E5.
- Pickup: 10 AM–8 PM daily, local Kitchener time. Wait for Ready for pickup confirmation and arrange a time before arriving. No ready-for-pickup notification or scheduling workflow has been implemented yet.
- Guest checkout is allowed; verified signed-in customers are attached to their own orders. Orders are never linked just by matching an email address.
- Latest owner information relayed by user (2026-10-28): business has no GST/HST number and reports revenue below $30,000, superseding the earlier registered-status statement. Small-supplier eligibility has not been independently verified. Do not add a fictitious registration. Use explicit CHECKOUT_TAX_MODE=sandbox_no_tax for testing without tax collection; this is not a production tax determination. Provincial obligations still require review.

## Setup, one step at a time

1. Run `supabase/checkout.sql` once after the product/size migrations. This creates private `store_orders` and three server-only RPCs. It makes no Stripe calls and does not change existing inventory until checkout starts.
2. Keep `STRIPE_SECRET_KEY=sk_test_...` and `SUPABASE_SECRET_KEY=sb_secret_...` only in `.env.local`/server secrets, never `NEXT_PUBLIC_` variables. The server secret is intentionally separate from the regular authenticated admin client; admin product actions keep their existing RLS enforcement. Environment files are ignored by version control.
3. Install/sign in to the official Stripe CLI and run a local listener:

   ```text
   stripe listen --events checkout.session.completed,checkout.session.expired,checkout.session.async_payment_succeeded --forward-to localhost:3000/api/stripe/webhook
   ```

   Put the listener's signing secret into `STRIPE_WEBHOOK_SECRET=whsec_...`. Keep the listener running during tests. Do not paste secrets into chat or source code. A deployed endpoint needs its own signing secret and an HTTPS URL.
4. Set `CHECKOUT_TAX_MODE=sandbox_no_tax` for the current sandbox: automatic tax is disabled, no tax registration is required, and the preview explains that no tax is collected for this test. Do not add a Canadian registration unless the business actually holds it. If testing a registered business later, use `CHECKOUT_TAX_MODE=automatic` plus `STRIPE_TAX_READY=true` only after configuring its real registration and checking product classifications in that sandbox. Missing/unknown modes disable checkout. Neither mode enables live keys.
5. After setup, use dedicated test products or an isolated staging database, then set `CHECKOUT_SANDBOX_ENABLED=true` in server environment and restart development. Checkout stays disabled without an explicit valid tax mode and test/server/webhook keys. Sandbox orders reserve and consume stock in the configured Supabase project. No-tax mode does not require STRIPE_TAX_READY.
6. Open `/cart` → Checkout, choose delivery or pickup, and pay using Stripe's official test card details. Never use a real card for sandbox testing. Check the private order page changes from pending to confirmed only after its signed notification arrives. Test decline, cancellation/resume, expiration, duplicate delivery, guest isolation and stock corrections.

Official references: [Stripe testing](https://docs.stripe.com/testing), [webhooks/local listener](https://docs.stripe.com/webhooks), [Checkout tax address priority](https://docs.stripe.com/tax/checkout/page), [Supabase secret keys](https://supabase.com/docs/guides/getting-started/api-keys).

## Security and stock flow

The browser submits product IDs, size, quantity, delivery method, a random request ID and, for custom test lines, saved design snapshots. Price, tax, user ID and shipping overrides are ignored. Requests require an exact trusted Origin, a bounded request body (24 MiB for custom artwork) and validated inputs; invalid snapshots, duplicate lines and oversized quantities are rejected. SITE_URL must be a configured trusted HTTPS origin in production, with localhost allowed only in development.

`store_checkout_start` runs transactionally, serializes a browser's attempts, locks products in ID order, reads current database prices/options, and reserves both total and per-size stock. Inventory is reduced immediately to prevent simultaneous checkouts from taking the same units. Identical pending carts reuse their order/reservation; completed request IDs cannot be reused. There is a five-orders-per-30-minutes browser limit. This is not adequate distributed abuse protection for a public launch: deleting the guest cookie changes this identity; add trusted infrastructure rate limits/CAPTCHA before exposure.

Guest receipt access requires a random 256-bit HTTP-only, SameSite=Lax cookie (Secure in production), with only its SHA-256 hash in the database. Verified account owners can also view their orders. Checkout RPCs remain server-role-only; direct order reads remain admin-only under RLS, with selected column grants and no app-user writes. Customer history uses the separate ownership-checked read RPC described below. Cookie access lasts 30 days; secure emailed guest access/account claiming remain future work. Customer details are stored privately after verified payment; do not put them in logs or project context notes.

Stripe customer/session creation use stable server idempotency keys. Pickup creates a Stripe customer with the fixed pickup shipping address so automatic tax uses the pickup location; the customer cannot edit a delivery address in that checkout. Delivery collects a Canadian shipping address. Billing/contact/payment details are entered on Stripe's hosted page. Redirects accept only HTTPS checkout.stripe.com URLs.

The webhook verifies the raw-body signature, refuses live events, retrieves the latest session from Stripe, and checks session binding, CAD currency, subtotal, shipping and total in the database before recording paid. A no-tax session must have server-created tax_mode=sandbox_no_tax metadata, automatic tax disabled and an explicitly zero tax total. Other sessions require enabled, finalized automatic tax. This uses the original verified session policy, independent of later environment changes. A redirect or client-supplied success flag cannot confirm payment. Database transitions are idempotent: paid stock is not deducted twice; paid orders ignore a late expiration; expired orders cannot be marked paid after stock release without manual investigation. Receipt updates remove only matching purchased product/size/design quantities from the local cart once, preserving other lines and extra quantities.

Stock is released only following a Stripe-confirmed expired session, never merely from returning to the cart or a local timer. Open sessions expire one hour after the reservation began. New Stripe sessions return to `/cart` when the customer leaves checkout; success still returns to the private receipt. Existing incomplete photo constraints can prevent inventory updates and must be resolved rather than weakened.

Unpaid items stay in the cart with Continue checkout and Remove controls; no separate pending-order screen is required. Cart refresh reads only pending orders matching the current browser's hashed HTTP-only receipt cookie, returning minimal item snapshots/order IDs without access hashes or contact details. Own reserved quantities preserve cart availability without changing public stock. Missing cart lines can restore from these verified snapshots. Reservation lookup failures preserve saved cart contents. Quantity changes/new checkout links are withheld until an existing checkout is finished or removed; other newly added lines stay saved. Continue checkout reopens the existing verified Stripe session and retains its original items, prices and delivery method. Sold-out public sizes still exclude held stock.

`POST /api/checkout/[id]` requires exact trusted Origin, bounded action input, and either the order's receipt cookie or a server-verified confirmed account owner. Resume checks bound session identity, sandbox mode and the safe Stripe URL. Remove first expires the entire unpaid Stripe session, retrieves its current state, and invokes the existing idempotent stock-release RPC only after verified expiration. It never refunds/cancels paid orders or blindly restores stock after a failed provider request. Removing one line closes that immutable checkout; other cart lines remain for a fresh checkout. Unknown creating sessions without a bound Stripe ID require reconciliation, not automatic cancellation. If stock settlement fails after Stripe closes, repeating Remove safely retries settlement. Duplicate webhook/cancellation settlements cannot release twice. Same-browser cookie recovery is supported; paid account history is described below.

## Customer order history

Run `supabase/customer-orders.sql` once as project owner in Supabase SQL Editor, after `order-management.sql`. Then open Account → Your orders (`/account/orders`) while signed in. The list shows 25 paid orders per page, newest first; each detail page shows purchased item snapshots, CAD totals and current delivery/pickup status. Dates use Kitchener time. Existing sandbox labels remain; no live payments are enabled.

Every list/detail request verifies the confirmed account on the server using the normal authenticated client. The read-only `store_customer_orders` security-definer RPC independently checks the current `auth.uid()` against a confirmed database user and selects only paid rows whose stored `user_id` matches. It uses an empty search path, fully qualified objects, bounded pagination and explicit return columns. It accepts no customer identity parameter, exposes no contact details, receipt hashes, Stripe IDs or fulfilment actor, and grants execution only to authenticated users. Existing admin restrictive RLS, table privileges, checkout RPCs and stock remain unchanged. Missing/foreign/guest/unpaid IDs return the same empty result and detail 404; database errors show a generic retry message without private details. Pages are dynamic and covered by private/no-store Proxy headers.

Only purchases made while signed in to that account appear, including earlier paid orders already linked at checkout. Guest purchases are not claimed by matching an email, signing in later, or supplying an order ID. Their existing cookie-authorized receipts continue to work. Customers have no fulfilment controls; current admin changes appear on the next page load. Notifications, tracking, automatic refresh and refunds are outside this feature.

After migration, verify a signed-in buyer can see their paid order and current status; a second account must receive 404 for its detail URL. Check empty history, pickup/shipping states and an admin update followed by customer refresh. Remote migration and signed-in verification remain pending. Local PostgreSQL tests cover cross-account/guest/unpaid denial, missing/unconfirmed identities, output field limits, pagination, unchanged admin rights and checkout reservations/payment transitions; page tests cover authentication, missing IDs, escaping, totals/status and generic failures.

## Operational limits before launch

- User verified existing migration objects and successful sandbox delivery/pickup purchases, cart cleanup, sold-out purchased size, provider decline, and successful retry on the same unpaid order (2026-10-28). CLI sandbox authentication/listener connection was agent-observed. Remote database policy definitions, live user verification of cart Remove/stock restoration, automatic expiration and duplicate-event delivery remain unverified. No-tax mode is test-only; live small-supplier eligibility/provincial obligations are unreviewed.
- A failed/uncertain Stripe request or session-binding failure can leave a **creating** reservation without a usable session. Never automatically release it: a payment session might have been created despite a lost response. An operator must reconcile with Stripe before restoring inventory. Build a scheduled reconciliation process and an admin review/release workflow before production. Keep the webhook listener running; monitor and replay failed events. Old creating reservations may need explicit reconciliation rather than retries once the original session expiry is too close/past.
- Admin stock counts represent available inventory after reservations. Operators must not overwrite these counts with physical totals without accounting for holds. Product deletion leaves immutable order snapshots but existing cascades/triggers still require an audit. Catalog data changes during a reservation require operational review.
- Paid-order admin viewing and fulfilment controls are implemented and user-verified at `/admin/orders`; see ADMIN.md. Customer paid-order history is implemented, pending the migration and signed-in verification above. No packing/shipping/ready notifications, email confirmations, paid-order refunds/cancellations, secure guest email links, automatic reconciliation job or production retention/backups policy is implemented. Cart Remove supports only verified cancellation of unpaid checkout.
- Live keys are deliberately blocked. Production needs a separately reviewed release covering pricing/tax, protected access, abuse controls, reconciliation, fulfilment, transactional email and deployment configuration.
